## 两个真实差异及共同修复范围

**C13**：上游 `_unload()` 在每个 disposer 前等待微任务；Python 原实现直接调用
同步 disposer。返回瞬间上游日志为 `[]`，Python 为 `["unloaded"]`。
旧 Python 测试恰好断言了过早清理，因此“原测试全绿”没有检测到差异。

修复：立即取出 effect 列表，但在有运行中 loop 时延迟执行清理；无 loop 时
保留原同步适配。该适配仍需未来单独的跨运行模型评估，不能声称 JS 原生存在
“无事件循环”场景。更新 C13 用例以检查真实调用边界及 await 后的最终清理。

**C14**：上游 `_updateState` 先保存 `_reload()` 的 inertia，再通知 LOADING。
Python 原实现先通知，再创建 Task。通知中的 dispose 因而看到没有在途加载，
提前推进卸载至 DISPOSED。上游调用返回时为 LOADING，Python 原来为 DISPOSED。

修复：先登记加载 Task，再通知 LOADING。重入 dispose 只使 epoch 失效，并等待
该加载跨过检查点后清理；插件本体不会执行。C14 用例不再要求提前终止。

消费者检查发现 publication-failure 回滚测试只等待一次 `sleep(0)`。修复后的
合法异步清理需要等待实际 settlement。回滚任务现在通过现有
`schedule_settlement()` 登记所有权，测试调用 `await_settled()` 检查完成，
避免增加 sleep 次数来掩盖未管理任务。

这些变化归入同一个生命周期契约修订 `CON-CORDIS-CORE@2`，未按文件目录
把消费者测试修复留给一个被核心阻塞的后续任务。
