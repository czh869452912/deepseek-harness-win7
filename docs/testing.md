# 开发验证与完整门禁

日常开发采用与改动范围匹配的定向验证。完整集合和发行门禁集中安排在候选稳定、准备整体签收时，避免把每次任务收尾都变成一次发行验收。本文与 `AGENTS.md` 第5节共同作为当前指引；历史进展记录里的“下一次全套待执行”等描述不自动触发新的完整运行。

## 验证节点

| 节点 | 默认验证 | 完整门禁安排 |
|---|---|---|
| 文档、开发指引修改 | 差异、链接及涉及的结构化配置检查 | 不因文档收尾启动 pytest |
| 单点修复、日常迭代 | 原失败用例、修改提供端、直接消费者和相关回归 | 不因提交、合并或 push 启动全套 |
| 插件或迁移子合同开发收尾 | 子系统合同、依赖/卸载/恢复及必要的真实 Source/native 配对 | 按该合同要求保留证据，不自动执行整个发行门禁 |
| 一批关联迁移准备统一签收 | 先完成各子项定向验证，协调写入并冻结候选 | 对稳定候选执行一次完整门禁 |
| 跨模块架构改造准备整体签收 | 覆盖受影响链路，例如 Cordis ownership、共享存储、协议和默认预设 | 在相关修改与局部问题收尾后执行一次完整门禁 |
| Portable 发布或完整发行签收 | 对冻结提交、完整输入和实际发行 ZIP 做统一验收 | 必须执行完整门禁；发布使用回执绑定的实际 ZIP |
| 用户明确要求完整回归或门禁 | 按其指定目标、范围和约束执行 | 独立全量 pytest 与完整发行验收分别报告 |

定向验证足以完成局部开发、提交与交接，但不能替代迁移任务已有的 acceptance 或缺失的统一签收证据。需要完整证据的任务保持相应未签收状态；不能通过修改指引自动提升台账。

## 每次任务如何选测试

开始验证前，说明变更影响、将执行的用例/模块/消费者，以及选择完整门禁时的触发原因。使用提供端和消费链路判断影响范围，包含必要的取消、卸载、冷恢复和跨载体控制；不能只看本次修改了哪些测试文件。

例如 SDK 帧等待 helper 的小修改，可先运行：

```powershell
.venv\Scripts\python.exe -m pytest tests/test_sdk_stdio_wait.py --durations=20
```

随后根据实际改动选择 `tests/test_sdk_stdio_journey.py` 的相关真实进程旅程。若只调整 SDK 观察器的长路径读取，应选择路径控制及 SDK 配对；如果同时改了 JSONL 存储，还需验证普通/zstd 写入、追加、冷读取、恢复和直接 SDK 消费者。这些例子不是固定的完整测试清单。

通过后，仅当新代码变动、发现失败或仍有未覆盖风险时继续扩测/重测。环境缺少依赖、一次局部失败或机器耗时不同，先定位对应问题；不要因此反复启动完整集合。

## 完整门禁的准备与失败处理

启动完整运行前，已知问题应已修复并经过定向验证；固定 Python/Node/原版依赖及实际浏览器应已准备好；写入者应已协调，正式候选应满足干净冻结要求。为该次运行选定新的输出目录，并明确要取得完整回归结果还是正式发行资格。

rc022 协调切换期间，当前 Source/配对清单见 [release-gate-plan.json](../migration/candidates/rc022/release-gate-plan.json)。`scripts/rc022_gate_runner.py` 的 Source/paired 通道支持显式子集，子集回执标为 `complete_lane=false`，所有独立通道均为 `release_acceptance=false`。旧 Node 22、旧 Source 的 21 组配置、82 个配对及其回执保持原身份；不能仅换 pin 后当作当前资格。新完整编排与实际解压/浏览器通道完成前，独立通道通过不构成发行签收，见[当前通道进展](../migration/candidates/rc022/current-gate-lanes-checks.json)。

`scripts/verify_release.py` 本身包括全量 Python 回归、固定原版 Source 配置、配对合同及同包实际解压/浏览器检查。正式统一门禁直接使用该入口，不在前面另外跑一次全量 pytest。单独执行全量 pytest 只证明其实际回归范围。

完整入口在 pytest 收集结束时检查实际参数化实例与必跑清单，缺失、重复或歧义会在测试体执行前拒绝，并写入 `pytest-collection.json`。该报告只证明收集身份；最终仍须用实际执行后的 XML 检查通过、跳过及必跑覆盖，不能以 collect-only 代替回归验收。

完整运行发现多项问题后，保留原始失败和用时，集中修复，并复验各失败及受影响消费者。下一次完整门禁安排在这些问题收尾后的稳定候选；不要每修好一个用例就重新跑全部集合。已有运行记录可用于诊断，不能把不同候选的通过片段拼成新的完整通过。

耗时长不直接等于死循环。先检查冷夹具构造、文件复制/打包、真实子进程启动、等待截止时间及重复或嵌套等待。当前发行入口默认不对整个 pytest 集合设置3600秒硬限制；只有显式 `--regression-timeout SECONDS` 才设置总预算，单项操作的连接、取消及子进程期限仍保留。

同一份完整合格回执只用于它实际绑定的候选提交、冻结输入和 ZIP。相同资格可以支持相应整合/发布节点，避免无理由重复运行；输入或候选变化后不得把旧回执重标为新产品签收。发布使用已验收 ZIP，不另行重建一个不同的包。

## 临时输出与证据

### 证据不再进入 LFS

日常开发、定向验证、提交和推送可以继续，不以远端历史 LFS 回收工单的完成状态作为门禁。开发者和 agent 必须遵守以下两点：

1. 测试日志、临时工作区和生成的大型证据 ZIP 使用新建的自有忽略目录（例如 `.goose/out/<run-id>/`），或测试运行器指定的仓库外工作区。保存必要观察及小型回执后，在同一任务内按下文保留规则清理无用资产；不得将这些临时输出加入 Git/LFS，包括使用 `git add -f`。正式大型材料进入 Release 附件或持久外部存储。
2. 审计完整历史证据或为旧版本检查准备输入时，只按位置映射从 Release 取回所需归档，核对原始索引中的尺寸和 SHA-256，存入 `DSH_EVIDENCE_ROOT`。旧提交可能仍有 LFS 属性，检查旧版时应关闭自动 LFS 下载；旧消费者若必须使用原路径，仅在隔离检出中还原所需输入，不将还原归档提交或上传，也不恢复批量 LFS 跟踪和默认全量下载。

历史测试 ZIP 存放在仓库外；Git 保存 `migration/storage/external-artifacts.json` 中的原路径、尺寸和 SHA-256。用 `DSH_EVIDENCE_ROOT` 指定镜像原路径的外部目录，不自动联网或下载整个历史档案。正式发行包及必要资格材料放在对应 Release 附件或持久外部存储；已解决调试材料设置保留期限，未解决失败和独有真实观察继续保留。原始回执及其候选身份不改写。

历史档案的实际下载地址、Release 标签及附件 ID 见 [位置映射](../migration/storage/external-locations.json)，远端发布与身份核验见 [迁移记录](research/2026-11-14-lfs-remote-migration.md)。映射只提供位置，原始身份仍以 `external-artifacts.json` 为准；下载单份材料后核对其尺寸及 SHA-256，并放在 `DSH_EVIDENCE_ROOT` 下对应原路径。下面的完整原件校验需要全部 240 份材料，缺失任何一份均失败，不是按需下载单份时必须执行的日常门禁。

```powershell
# 离线结构校验，不证明原始证据字节存在或测试通过。
.venv/Scripts/python.exe scripts/evidence_assets.py check
.venv/Scripts/python.exe scripts/migration.py check
.venv/Scripts/python.exe scripts/migration.py ready

# 显式核验仓库外原始材料，缺失或损坏必须失败。
$env:DSH_EVIDENCE_ROOT = 'D:\archives\deepseek-harness-win7-evidence'
.venv/Scripts/python.exe scripts/evidence_assets.py verify
.venv/Scripts/python.exe scripts/migration.py check --verify-artifacts
```

默认台账检查只验证外部资产索引，并显示 `external-bytes-unverified`；这类记录不提供当前验收资格。完整字节校验是独立操作，也不等于重新运行历史测试或取得新候选发行资格。只有验证过尺寸及完整 SHA-256 的原始副本才能替代工作树中的归档。按需恢复到旧路径的 ZIP 被 `.gitignore` 排除，禁止强制添加回源码仓库。

日常回归使用 `tests/fixtures/evidence` 中按原字节提取的最小 JSON 成员，gzip 仅用于无损减小体积；manifest 保存原归档和成员 SHA-256。固定前端的冷恢复使用仓库已保存的原构建成员、完整构建摘要和原构建记录，不依赖历史测试 ZIP。CI 默认关闭 LFS 下载。

### 输出保留与清理

为有实际验证价值的运行保留命令、范围、退出状态、XML/日志和用时。完整门禁还需保留冻结输入、候选身份、实际 ZIP 和必要的原始观察。失败时及时保存定位所需原始材料；未得到完整 XML 的中断运行不能声称最终通过数量。

定向运行通常使用 `tests/conftest.py` 已配置的 `.goose/out/t-*` 新短工作区；完整门禁使用系统临时目录下映射明确的 `g-*` 短工作区，执行位置必须在仓库外。结束后原子移动到本次输出的 `pytest-workspace`，保留失败原文和运行路径。系统临时目录与输出须在同一卷；否则启动前拒绝，请把 `TEMP` 指向输出卷上的仓库外目录。若手工指定 `--basetemp`，必须是该次运行新的自有目录，不能复用未结案失败或其他任务的目录，因为 pytest 会清空指定目录。日志/XML也应使用新的输出身份。

现有 `scripts/process_artifact_retention.py` 只清理归属及完成状态可验证的合成回执和原样副本。定向 pytest 正常结束会清理已明确识别的合成回执；完整门禁另有父进程收尾和前检副本维护。适用的已结束发行目录可以通过该脚本的 `--output` 入口维护，不能把任意定向目录当作满足发行工作区映射的目录。

修改执行目录或归属映射时，应通过真实 `run_python_regression` 外部门禁入口复验嵌套子进程、保留控制和搜索回执直接消费者。嵌套正例必须声明自己的映射，不能继承父owner后把任意子目录当作已获授权；预期失败须检查逐子XML，单看退出码1可能漏掉第二个失败。搜索回执绑定调用方预先选择的精确目录，不能仅要求位于产品父目录或广泛允许系统临时目录。完成/失败/未完成的审计分别统计，负例审计保留原状。

FS公共值配对的物理夹具由 `scripts/fs_fixture_workspace.py` 分配到仓库外短系统临时目录，原始观察保留在运行输出中。提供端完成后登记所有权、完整观察SHA、文件/目录清单；最后一个实际消费者结束后才核验删除。未完成、不匹配、改变观察/文件、未知文件/目录、reparse或共享硬链接均拒绝；清理失败使对应验证失败，保留失败审计。只读附件对象仅在归属及字节核验通过后解除该夹具的只读位。不要用通配符删除系统临时目录，也不要在Portable或晚校验之前删除仍需消费的夹具。

正式证据归档应满足相应合同需要，不为每次局部修复重新构建 Portable，也不把每轮调试工作区整体归档进入 LFS。真实 Source/浏览器观察、未查明失败、正式回执、活动/未知文件和受保护的原历史备份继续保留。清理依据所有权、分类、核验和审计，禁止直接递归删除整个 `.goose/out`。

原始 JSON/Host 输出、解压副本、正式 ZIP、写入中的证据 JSON 与 Git LFS 缓存会同时占空间。前检按实际观测峰值准备余量，不能只计算最终 ZIP 大小；前检不足就暂停写入，不重复耗尽磁盘。NTFS 压缩只能减少物理占用，所有普通读取字节与 SHA 必须保持。退休已封存原始观察的散装重复副本时，须先核对正式归档身份、成员完整性、逐项尺寸/SHA并记录 archive/member；失败/截断字节和原退出码在归档中原样保留。独立有限合同可复用同候选、同输入、同包的已完成独立子进程原始证据，缺失旅程单独补验；原外层失败仍是失败，不能拼成新的完整通过。台账应用采用可靠空间前检；失败准备记录只有在未引用且可逐字节重建时才能回退，原失败文件/日志和已完成审查继续保留。

## Desktop 安装与真实服务的独立检查

`scripts/verify_desktop_lifecycle.py --plan <json> --node <pinned-node> --output <fresh-directory>` 消费实际 Standard/AIO 安装器；plan 的 `lanes` 每项包含 `id`、绝对 `installer` 路径和可选的绝对 `previous` 安装器路径。观察器发起一次 UAC，在隔离安装目录执行管理员安装/覆盖升级、发布失败回滚、普通用户 GUI fresh/cold 和卸载。原机器注册表及开始菜单快捷方式先备份，最终恢复；不把真实用户历史传给安装器。历史专用测试目录清理必须显式列入 `cleanupRoots`，只清理已核验清单和空目录，遇到未知文件保留并报错。

真实服务检查显式启用并提供仓库外凭据文件：`scripts/verify_live_provider.py` 验证 canonical CLI/工具/独立进程恢复，`scripts/verify_live_desktop_provider.py` 验证实际原版 Desktop 输入框、真实读文件工具与冷启动上下文。后者接受 `--executable`、`--node`、`--credentials-file`、`--output`；仅开发观察增加 `--development-python`。两者只发送生成的探针文档，凭据只进入子进程环境；含私有 home 的原始运行目录不整体归档。实际 provider 检查不代替离线回归，开发外壳结果也不代替精确包内程序结果。

`scripts/oracles/desktop_visual_matrix.mjs` 比较固定原版 renderer 在 Electron22/44、两种 locale/主题和三种模拟缩放下的 120 份视图。两侧使用同一 Python Host；明确排除上游 npm Host、原生 OS DPI 和所有系统弹窗逐像素资格。闭合 `details` 的内部控件按实际不可见处理，不能仅依靠 Chromium108 返回的内部矩形计入可见控件。保留原图、控件顺序、尺寸、焦点与弹窗状态，以及浏览器原生控件的度量差异。

内网更新演练和真实发布分开，见[部署与验证说明](desktop-lan-updates.md)。没有长期密钥/服务器地址时，不把本机 HTTPS 夹具标成已发布通道。

## 当前 CI 的边界

当前 `.github/workflows/verify.yml` 仍在 PR、手工调用及发布复用时执行完整发行门禁，整体job期限为180分钟；先准备固定Chromium108观察器，与现代浏览器共同传入发行入口。完整入口新增同ZIP包内Python的108三预设fresh/cold功能旅程和输入/模块/缺lane拒绝；这不替代其他realm/CSS审计或Win7认证。`.github/workflows/release.yml` 的发布依赖同一验收产物和精确ZIP散列，不另行重建。

CI诊断先由 `scripts/package_release_diagnostics.py` 封装，再只上传单一ZIP，避免上传器遍历测试链接。普通文件保留原字节和清单，symlink/junction/reparse自身记录原始目标或reparse数据而不跟随；原工作区不删除。失败摘要在封装前直接输出到CI日志；缺失/截断XML不得推断最终计数。GitHub artifact 下载ZIP包含这个诊断ZIP，消费时应分别绑定外层传输校验和与内层原始诊断载体，不把传输封装误当成新的验收。

完整封装失败时另以 `--reports-only` 保留根目录XML/日志/观察，清单明确披露未保留的嵌套目录，封装步骤仍返回原失败并阻止发布。Windows可执行文件的lstat由扩展名合成执行位，fstat不含该位；身份核对比较对象类型、设备/inode、尺寸及时间，而不要求这两类权限位相同，尺寸变化仍拒绝。CI检出前固定 `core.symlinks=false`，绑定Windows源码符号链接文本落盘方式；依赖准备后先实际核验Source全部guarded输入，避免到全量pytest才发现目录链接读取失败。

后续 CI 改造应单独实现普通 PR 的相关验证与稳定整合/发布的完整门禁，评估 runner 的实际耗时，并保持正式回执、必需 lane 和精确 ZIP 发布约束。在 CI 改造完成前，应按现有工作流实际结果报告。
