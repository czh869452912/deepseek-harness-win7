# 仓库证据存储与退出 LFS 评估

评估日期：2026-11-14。只读盘点候选 `0e58297cb4869014662135c6ace7e96b29fd723e`，未下载远端 LFS 对象、删除证据、改写 Git 历史或修改 CI。工作区原有 `.gitignore` 修改保留。

## 结论

不建议继续把完整历史测试工作区作为源码资产长期存入 Git/LFS。建议采用“源码仓库保存小型回执、索引和必要回归夹具，正式发行附件保存发行包与关键验收原始材料，历史调试材料移至仓库外归档并设保留期限”的组织方式。项目可以退出 LFS；当前 LFS 没有承载产品运行必需的代码或二进制。

保留证据的真实性、候选绑定和可追溯性有必要；让所有开发者和 CI 默认下载全部证据没有必要。移出 Git 不等于销毁证据，也不能把历史失败改成成功或把旧资格重新绑定到新提交。

LFS 归档中央目录统计还显示 JSON 成员压缩后约 3.24 GB。对 Portable 成员按尺寸和 CRC 分组，可发现重复候选，但 CRC 不是密码学身份，本轮没有据此认定任何文件可安全删除。

实施期间补查了 `git rev-list --objects --all` 与 `git cat-file --batch-check`：本地 refs 可达普通文件 blob 的实际存储量合计约 209 MB，其中 evidence JSON 约 53 MB、历史普通 ZIP 约 32 MB、其他文件约 123 MB（不含 pack 索引/树/提交等开销，非远端账单）。因此不能把本地 6.13 GiB pack 当作当前源码仓库的必要传输量；其余对象可能涉及历史重写遗留及 reflog/保护性保留，本轮不做垃圾回收。601 MB 回执是未压缩逻辑体积，当前优先保留原字节，先解决 13.59 GB 的 LFS 配额，不为了压缩 JSON 而立即进行大规模历史改写。

几个代表性样本：

- `HANDOFF-PARENT-REVIEW-20261010-F90DED26.zip`：约 768 MB，内部又保存了约 346 MB 的 `ui-v4-v5-v6-rejection-snapshots-v1.zip`，另有多个大型原始 JSON。
- `SESSION-STORAGE-20261005-1f180e40.zip`：约 685 MB，包含多个不同阶段的 `candidate-portable.zip`，其中多份各约 76 MB。
- `SESSION-QUERY-ENGINE-20261004-5c8c2c57.zip`：约 631 MB，混合多个相关子任务工作区和候选 Portable。

这表明主要问题是归档粒度、嵌套打包和保留策略；换一种压缩格式或仅删除几个最大文件不能长期解决。

## 建议的资产边界

| 材料 | 建议位置与保留规则 |
|---|---|
| 代码、锁文件、上游 pin、构建/测试脚本 | 普通 Git，长期保留 |
| 小型回归夹具、必要 golden 和协议样本 | 普通 Git；从大归档提取测试实际使用的成员，保留原始来源、成员路径及 SHA-256 |
| 验证结论与索引 | 普通 Git；只保留 run ID、候选、命令、环境概要、结果、范围、外部资产地址/身份、尺寸与 SHA-256 |
| 正式发布的 Portable/安装器 | 对应 GitHub Release 附件；同一字节资产尽量只有一个权威副本 |
| 正式里程碑的关键原始观察/完整资格材料 | Release 附件或具有持久保留能力的外部存储；按需下载核验，避免默认 clone 下载 |
| 已解决问题的历史失败、阶段调试输出 | 先迁往仓库外历史档案；索引标记历史身份，建议保留 30–90 天后复审，不自动全量永久保存 |
| 未解决失败、独有真实系统观察、受保护历史备份 | 保留，有负责人、用途及下一复审节点；可在仓库外，不直接删除 |
| 可重建合成夹具、解压副本、浏览器缓存 | 最后消费者结束后按现有所有权/校验规则清理，不作为长期证据上传 |

30–90 天是建议的新策略，不是现有材料的删除授权。当前 `AGENTS.md` 和 `docs/testing.md` 要求保留真实观察、未解决失败、正式回执与历史备份；迁移应先明确外部保存规则，再处理各资产，不能直接递归删除证据目录。

## 必须先处理的代码耦合

1. `scripts/migration.py` 对每份 evidence 的 artifact 路径执行本地 SHA 校验；`scripts/migration_storage.py` 还验证历史 LFS 转换证明及原归档字节。直接删除 ZIP 会破坏台账检查。建议分离离线索引结构校验与显式完整材料校验；材料未取回时应报告“未核验”，不能默认通过。历史回执保持原字节，以旁路位置映射关联外部存储。
2. `tests/test_engine_composition_consumers.py`、`tests/test_route_execution_consumers.py`、`tests/test_rc3_engine_route_current.py` 直接打开大型归档并校验其整体哈希。应提取实际使用的最小成员及来源清单，让日常回归独立于历史档案；归档整体核验留给按需审计。这三个文件是已发现实例，不声称已穷尽所有间接消费者。
3. `.github/workflows/verify.yml` 和 `release-environment.yml` 配置 `lfs: true`。消费者调整后取消默认 LFS 下载；正式验收只获取该次必需材料。GitHub Actions 下载 LFS 同样消耗仓库所有者带宽。
4. 普通 Git 的大型 evidence JSON 也应检查重复清单和内联观察。新回执引用共享内容寻址清单；已有签署回执不就地删字段，完整原件先外存，另建紧凑索引。否则取消 LFS 后仍留下较重源码树。
5. 保留运行需要的 ICU DLL、rg 等产品资源。当前最大非证据文件约 33 MB，按本轮文件规模，退出 LFS 没有明显的产品二进制阻碍。

## 执行顺序及历史处理

1. 立即停止新增整轮工作区归档；先确定仓库外备份位置和长期正式资产位置。不要先取消 LFS 规则后把 13.59 GB ZIP 直接提交成普通 Git blob。
2. 生成可机器核验的迁移清单：原路径、LFS OID、尺寸、SHA-256、引用者、保留分类、目标位置、迁移验证结果。逐项复制并验证后再移除跟踪；外部上传和长期可访问性也需要实际核验。
3. 完成最小测试夹具、台账/历史证明解析和 CI 消费端改造，更新开发指南。定向运行受影响消费者与迁移检查，验证全新无 LFS checkout 可执行日常回归；下一稳定候选再做完整资格，不能把本次盘点当作验收。
4. 先用普通提交使当前分支不再依赖 LFS。这可以阻止继续增长及默认下载，但历史对象仍计费。
5. 若还需缩减普通 Git 历史，在隔离镜像副本中试做历史清理，涵盖历史直接存储的大 ZIP 和相关分支/标签。现有 archive 标签与历史转换证明必须一起设计迁移；只清理 master 不足以释放仍被其他 refs 引用的对象。记录旧/新提交映射，保留原候选身份、签收语义和仓库外历史备份，提前处理发行标签/链接/协作者重新 clone 的影响。
6. 服务端 LFS 配额回收单独处理。GitHub 官方说明：从历史删除后对象仍可能计费；可联系 Support 协助，或删除并重建仓库。删除重建会影响 issues、stars、forks 等，不能作为默认操作。Support 是否能处理本仓库应取得实际答复，不能承诺历史改写后账单立即归零。

历史改写、强推、删除/重建 GitHub 仓库均不在本次评估操作范围。优先争取保留现有仓库并由 Support 清理；如果不可行，再比较迁往新干净仓库与重建现有仓库的成本。单纯新建源码仓库而留下旧仓库 LFS，对原账户配额不会自动有帮助。

## GitHub 规则依据

- [Git LFS billing](https://docs.github.com/en/billing/concepts/product-billing/git-lfs)：每个更新版本按完整对象计量；下载（包括 Actions）计入所有者带宽。远端账单还可能包含本地 refs 不可见的对象。
- [Removing files from Git LFS](https://docs.github.com/en/repositories/working-with-files/managing-large-files/removing-files-from-git-large-file-storage)：移除跟踪/历史不等于清除远端对象；官方列出的后续途径是删除重建或联系 Support。
- [About releases](https://docs.github.com/en/repositories/releasing-projects-on-github/about-releases)：发行附件单文件须小于 2 GiB、每个 Release 最多 1,000 个附件；文档未设 Release 总体积及带宽上限。适合实际发行与正式验收材料，不建议把所有临时调试输出无限转移过去。
