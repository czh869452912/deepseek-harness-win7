# 开发验证与完整门禁

日常开发采用与改动范围匹配的定向验证。完整集合和发行门禁集中安排在候选稳定、准备整体签收时，避免把每次任务收尾都变成一次发行验收。本文与 `AGENTS.md` 第5节共同作为当前指引；历史进展记录里的“下一次全套待执行”等描述不自动触发新的完整运行。

## 验证节点

| 节点 | 默认验证 | 完整门禁安排 |
|---|---|---|
| 文档、开发指引修改 | 差异、链接及涉及的结构化配置检查 | 不因文档收尾启动 pytest |
| 单点修复、日常迭代 | 原失败用例、修改提供端、直接消费者和相关回归 | 不因提交、合并或 push 启动全套 |
| 插件或迁移子合同开发收尾 | 子系统合同、依赖/卸载/恢复及必要的真实 Source/native 配对 | 按该合同要求保留证据，不自动执行整个发行门禁 |
| 一批关联迁移准备统一签收 | 先完成各子项定向验证，协调写入并冻结候选 | 对稳定候选执行一次完整门禁 |
| 跨模块架构改造准备整体签收 | 覆盖受影响链路，例如 Cordis ownership、共享存储、协议和默认预设 | 在相关修改与局部问题收尾后执行一次完整门禁 |
| Portable 发布或完整发行签收 | 对冻结提交、完整输入和实际发行 ZIP 做统一验收 | 必须执行完整门禁；发布使用回执绑定的实际 ZIP |
| 用户明确要求完整回归或门禁 | 按其指定目标、范围和约束执行 | 独立全量 pytest 与完整发行验收分别报告 |

定向验证足以完成局部开发、提交与交接，但不能替代迁移任务已有的 acceptance 或缺失的统一签收证据。需要完整证据的任务保持相应未签收状态；不能通过修改指引自动提升台账。

## 每次任务如何选测试

开始验证前，说明变更影响、将执行的用例/模块/消费者，以及选择完整门禁时的触发原因。使用提供端和消费链路判断影响范围，包含必要的取消、卸载、冷恢复和跨载体控制；不能只看本次修改了哪些测试文件。

例如 SDK 帧等待 helper 的小修改，可先运行：

```powershell
.venv\Scripts\python.exe -m pytest tests/test_sdk_stdio_wait.py --durations=20
```

随后根据实际改动选择 `tests/test_sdk_stdio_journey.py` 的相关真实进程旅程。若只调整 SDK 观察器的长路径读取，应选择路径控制及 SDK 配对；如果同时改了 JSONL 存储，还需验证普通/zstd 写入、追加、冷读取、恢复和直接 SDK 消费者。这些例子不是固定的完整测试清单。

通过后，仅当新代码变动、发现失败或仍有未覆盖风险时继续扩测/重测。环境缺少依赖、一次局部失败或机器耗时不同，先定位对应问题；不要因此反复启动完整集合。

## 完整门禁的准备与失败处理

启动完整运行前，已知问题应已修复并经过定向验证；固定 Python/Node/原版依赖及实际浏览器应已准备好；写入者应已协调，正式候选应满足干净冻结要求。为该次运行选定新的输出目录，并明确要取得完整回归结果还是正式发行资格。

`scripts/verify_release.py` 本身包括全量 Python 回归、固定原版 Source 配置、配对合同及同包实际解压/浏览器检查。正式统一门禁直接使用该入口，不在前面另外跑一次全量 pytest。单独执行全量 pytest 只证明其实际回归范围。

完整运行发现多项问题后，保留原始失败和用时，集中修复，并复验各失败及受影响消费者。下一次完整门禁安排在这些问题收尾后的稳定候选；不要每修好一个用例就重新跑全部集合。已有运行记录可用于诊断，不能把不同候选的通过片段拼成新的完整通过。

耗时长不直接等于死循环。先检查冷夹具构造、文件复制/打包、真实子进程启动、等待截止时间及重复或嵌套等待。当前发行入口默认不对整个 pytest 集合设置3600秒硬限制；只有显式 `--regression-timeout SECONDS` 才设置总预算，单项操作的连接、取消及子进程期限仍保留。

同一份完整合格回执只用于它实际绑定的候选提交、冻结输入和 ZIP。相同资格可以支持相应整合/发布节点，避免无理由重复运行；输入或候选变化后不得把旧回执重标为新产品签收。发布使用已验收 ZIP，不另行重建一个不同的包。

## 临时输出与证据

为有实际验证价值的运行保留命令、范围、退出状态、XML/日志和用时。完整门禁还需保留冻结输入、候选身份、实际 ZIP 和必要的原始观察。失败时及时保存定位所需原始材料；未得到完整 XML 的中断运行不能声称最终通过数量。

定向运行通常使用 `tests/conftest.py` 已配置的 `.goose/out/t-*` 新短工作区；完整门禁使用系统临时目录下映射明确的 `g-*` 短工作区，执行位置必须在仓库外。结束后原子移动到本次输出的 `pytest-workspace`，保留失败原文和运行路径。系统临时目录与输出须在同一卷；否则启动前拒绝，请把 `TEMP` 指向输出卷上的仓库外目录。若手工指定 `--basetemp`，必须是该次运行新的自有目录，不能复用未结案失败或其他任务的目录，因为 pytest 会清空指定目录。日志/XML也应使用新的输出身份。

现有 `scripts/process_artifact_retention.py` 只清理归属及完成状态可验证的合成回执和原样副本。定向 pytest 正常结束会清理已明确识别的合成回执；完整门禁另有父进程收尾和前检副本维护。适用的已结束发行目录可以通过该脚本的 `--output` 入口维护，不能把任意定向目录当作满足发行工作区映射的目录。

FS公共值配对的物理夹具由 `scripts/fs_fixture_workspace.py` 分配到仓库外短系统临时目录，原始观察保留在运行输出中。提供端完成后登记所有权、完整观察SHA、文件/目录清单；最后一个实际消费者结束后才核验删除。未完成、不匹配、改变观察/文件、未知文件/目录、reparse或共享硬链接均拒绝；清理失败使对应验证失败，保留失败审计。只读附件对象仅在归属及字节核验通过后解除该夹具的只读位。不要用通配符删除系统临时目录，也不要在Portable或晚校验之前删除仍需消费的夹具。

正式证据归档应满足相应合同需要，不为每次局部修复重新构建 Portable，也不把每轮调试工作区整体归档进入 LFS。真实 Source/浏览器观察、未查明失败、正式回执、活动/未知文件和受保护的原历史备份继续保留。清理依据所有权、分类、核验和审计，禁止直接递归删除整个 `.goose/out`。

## 当前 CI 的边界

当前 `.github/workflows/verify.yml` 仍在 PR、手工调用及发布复用时执行完整发行门禁，整体job期限为180分钟；先准备固定Chromium108观察器，与现代浏览器共同传入发行入口。完整入口新增同ZIP包内Python的108三预设fresh/cold功能旅程和输入/模块/缺lane拒绝；这不替代其他realm/CSS审计或Win7认证。`.github/workflows/release.yml` 的发布依赖同一验收产物和精确ZIP散列，不另行重建。

后续 CI 改造应单独实现普通 PR 的相关验证与稳定整合/发布的完整门禁，评估 runner 的实际耗时，并保持正式回执、必需 lane 和精确 ZIP 发布约束。在 CI 改造完成前，应按现有工作流实际结果报告。
